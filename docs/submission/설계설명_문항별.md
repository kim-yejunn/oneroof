# 설계 설명 문항별 원고 (각 1,000자 이내)

문항 원문은 제출 화면에만 있어 A04 양식 순서(1~6절)에 맞춰 썼다. 제출 화면의 문항이 다르면 가장 가까운 원고를 붙이고 다듬는다.
글자 수는 공백 포함, 각 원고 끝에 표기.

---

## 문항 1. 문제와 전문성 확장 요약

OneRoof는 Corevia 판매장려금을 지급하기 전에 관련 거래처를 묶어 한도를 지키게 하는 운영 시스템입니다. 사용자는 한 달 장려금을 접수해 대리점별 월 200만 원 이하를 전결하는 영업지원팀, 한도를 넘는 건을 승인·반려하는 영업임원, 연체 대리점의 장려금을 상계할지 정하는 회계·자금팀입니다.

원본 정책은 대표자·주소·정산계좌 중 2개 이상 겹치면 합산해 한도를 적용하라고 하지만, 정산은 대리점 단위로 올라옵니다. 그래서 D-011·D-024·D-037 그룹(6월 합산 3,888,097원)이 1~5월 내내 전결로 지급됐습니다. 마스터, 지급표, 실제 입금 계좌, 미수금 연령표가 흩어져 있고, 정정·반려 뒤 무엇을 다시 볼지도 정해져 있지 않았습니다.

시스템은 정산 접수부터 관련자 판정, 합산 한도, 승인 라우팅, 소명·계좌 확인, 상계, 지급, 은행 회신, 감사 기록까지 상태를 이어 바꿉니다.

필수 확장은 연체 미수금 상계입니다. 지급 직전 90일 넘은 연체를 조회해 상계 제안액을 계산하고, 회계·자금팀이 상계나 전액 지급을 판단하면 지급액·미수금·통지 상태가 바뀝니다. 다른 부서 영향은 회계·자금팀의 회수 목표입니다. 영업 승인이 끝난 건도 회계·자금 결정 없이는 지급되지 않습니다. 개선 효과는 원본 6월 기준으로 확인했습니다. 합산 누락 없이 그룹이 임원에게 갔고, 상계 21곳 20,806,770원으로 현금 지급이 37,159,812원에서 16,353,042원이 됐습니다.

(732자, 공백 포함)

## 문항 2. 업무모델과 데이터

핵심 객체는 대리점, 식별정보 이력, 실제 입금, 장려금, 검토, 승인 요청, 소명·확인 요청, 회신 해석, 지급 지시, 미수금, 미수금 조정, 감사 기록입니다.

관련자는 대표자·주소·정산계좌 중 2개 이상 일치를 전이적으로 묶어 판정하고, 계좌는 마스터 값과 실제 입금 계좌를 함께 대조합니다. 근거마다 마스터 등록인지 실제 입금 계좌인지 남깁니다. 그룹은 저장하지 않고 적용일이 있는 식별정보 이력에서 매번 계산합니다. 그래서 "그 달 말 기준"으로 다시 판정할 수 있습니다. 원본 결과는 그룹 1개(D-011·D-024·D-037)와 근접 쌍 1개(D-034·D-041)입니다.

한도 200만 원, 관련자 합산, 임원 승인 권한은 원본 정책 그대로 두었고, 권한 없는 역할의 결정은 서버가 거부합니다. 상태는 검토(승인 대기·소명 대기·재상신·감사 이관·재분류)와 지급 지시(상계 검토·상계 완료·보류·전송·지급 완료)로 나눴습니다. 단계 사이는 이벤트로 잇고, 이벤트는 같은 트랜잭션으로 저장합니다.

변경의 영향도 모델이 확인합니다. 마스터 정정이 오면 결정 전 검토는 대체·재상신하고, 이미 전결로 지급된 달은 되돌리지 않고 임원 사후 확인을 만듭니다. 모의 입금이 오면 결정 전 상계 제안을 새 잔액으로 다시 올립니다.

원본 4개 파일(대리점 마스터, 입금 이력, 장려금 지급표, 미수금 연령표)은 복사본으로만 쓰고 체크섬으로 검증합니다. 계약서와 지급 수취계좌는 원본에 없어, 상계 조항·90일 기준·계좌 확인 규칙을 교육용 가정으로 표시했습니다.

(765자, 공백 포함)

## 문항 3. 대표 실행 사례

정상: 6월 장려금 40건을 접수하면 37건은 영업지원팀 전결로, RPG-D-011 합산 3,888,097원은 영업임원으로 상신됩니다. 37건을 일괄 승인하면 19건은 은행에 대량이체로 가고, 90일 넘게 연체된 18곳은 회계·자금 상계 검토로 갑니다. 모의 은행 회신 뒤 시스템이 지급 완료로 바꿉니다.

조건 변경: D-041 주소를 D-034와 같게 정정하면 새 그룹 RPG-D-034가 생기고, 이미 전결로 지급된 1·2·3·6월에 영업임원 사후 확인 4건이 생깁니다. 상계 결정 전에 D-034가 연체 800만 원을 입금하면(모의), 상계 제안이 1,353,657원에서 1,038,360원으로 다시 계산돼 올라갑니다.

승인 거절: 영업임원이 그룹을 반려하면 확정하지 않고 세 대리점에 관계 소명을 요청합니다. 소명 회신(모의)이 오면 AI가 원문을 구조화해 "정산계좌 공유 사유 미답변"을 짚고, 2차 상신 화면에 체크리스트로 보입니다. 영업임원이 확인한 항목은 결정 사유와 감사 로그에 남습니다. 2차 반려나 무응답이면 감사로 넘기고 장려금은 보류합니다.

정보 부족: 실입금 계좌가 등록 계좌와 다르면 지급을 보류하고 계좌 확인을 요청합니다. 무응답이면 보류를 유지하고 감사로 넘깁니다. D-012가 반품 120만 원 미반영을 이유로 상계에 이의를 제기하면(모의), 회계·자금팀이 재검토해 상계를 취소하고 미수금을 되살린 뒤 547,490원을 지급합니다.

모든 숫자는 원본 데이터로 계산한 값입니다. 같은 순서를 반복 실행해 매번 같은 결과를 확인했고, 사례마다 통합 테스트가 있습니다.

(785자, 공백 포함)

## 문항 4. 추가 확장

필수 확장(연체 미수금 상계) 외에 다음을 구현했습니다.

1) 지급 계좌 확인 보류(실제 작동, 회신은 모의): 원본 W07은 회수 계좌를 지급 계좌로 단정하지 말라고 합니다. 실입금 계좌가 등록 계좌와 다르면 지급을 멈추고 확인합니다. 원본에서는 D-024가 해당합니다.

2) 마스터 정정 소급 처리(실제 작동): "정정 뒤 어디까지 다시 볼 것인가"에 답합니다. 결정 전 검토는 대체·철회·재상신하고, 지급된 달은 되돌리지 않고 사후 확인만 요청합니다. 정정 값이 그 달 말 연결의 근거일 때만 발견으로 봐서, 무관한 정정이 과거를 흔들지 않게 했습니다.

3) 관계 소명과 감사 이관(실제 작동, 회신은 모의): 반려를 부정 확정이 아니라 소명 절차로 바꿨습니다. 감사 이관은 이번 회차의 종료일 뿐 후속 확인 의무의 종료가 아니라고 기록합니다.

4) AI 회신 해석과 결정 체크리스트(실제 작동): Gemini가 회신을 구조화합니다. 원문에 없는 금액·증빙은 검증에서 빼고, 혼잡하면 다음 모델, 실패하면 규칙 기반으로 대체합니다. 결정자가 체크한 항목이 기록에 남아 AI 제안이 어떻게 쓰였는지 추적됩니다.

5) 처리 안정성(실제 작동): 사건 ID로 중복 반영을 막고, 처리 중 버튼을 잠급니다. 일괄 처리는 사용자 행동 하나가 이벤트 하나가 되게 묶었습니다. 막힌 이벤트는 다시 보냅니다. 0.5코어 컨테이너에서 37건 승인부터 은행 전송까지 0.8초가 걸립니다.

6) 결산 연계(미지급 장려금 충당)와 출하 보류(연체 신용 한도)는 설계 단계입니다.

(768자, 공백 포함)

## 문항 5. 실행·재현 방법

결과물은 https://oneroof-17dq.axhub.app 이고 로그인이 없습니다. 화면 오른쪽 위에서 영업지원팀·영업임원·회계·자금팀을 바꿔 가며 씁니다. API 문서는 /swagger-ui.html 입니다. 소스는 Spring Boot 4.1(Java 21)·Spring Modulith·PostgreSQL과 React 화면이고, Docker 이미지 하나로 AXHub에 배포했습니다.

원본은 참가자 파일 4개를 복사해 두었습니다. 빈 DB로 시작하면 웹 서버가 열리기 전에 자동 적재하고 체크섬을 검증합니다.

대표 순서는 다음과 같습니다.
① 영업지원팀: 처리할 일에서 "정산 접수", "한도 이내 37건 일괄 승인", 지급에서 "이체 완료 회신"
② 영업임원: RPG-D-011 반려
③ 영업지원팀: 변경·예외 요청 카드에 소명 회신 입력
④ 영업임원: 재상신 건의 체크리스트를 확인하고 승인
⑤ 회계·자금팀: 채권·상계에서 켬·끔 비교 확인, "상계 제안 일괄 결정"
⑥ 변경·예외에서 D-012 상계 이의 입력, 회계·자금팀 재검토

마스터 정정은 변경·예외의 "시연 예시 채우기", 입금은 채권·상계 대리점 행의 "입금"입니다. 모의 회신은 은행이 지급 화면 버튼, 대리점이 요청 카드의 회신 버튼("기한 경과"는 무응답)입니다.

결과는 각 화면의 상태 배지, 정산 현황, 감사 로그 검색, 조회 API로 확인합니다. 로컬은 키를 설정하면 시연 도우미에서 초기화할 수 있습니다. 공개 서버는 초기화가 꺼져 있어 한 번 처리한 상태가 남습니다. 테스트는 46개입니다.

(776자, 공백 포함)

## 문항 6. 원본·가정 구분과 정보 공백 처리

화면과 감사 로그의 모든 값에 원본·부서 주장·가정·모의 회신·계산 결과·AI 생성 중 하나의 출처 배지가 붙습니다. 원본 폴더는 수정하지 않고, 필요한 4개 파일만 복사본으로 쓰며 체크섬 테스트로 확인합니다. 모든 행은 파일과 줄 번호를 가집니다.

원본 제약은 가정으로 바꾸지 않았습니다. 한도 200만 원, 관련자 합산, 임원 승인 권한은 원본 정책 그대로입니다. 원본에서 반려된 장려금은 합산에서 뺐습니다.

원본에 없는 정보는 이렇게 처리했습니다.
① 대리점 계약서(상계 근거): 상계 조항과 상계 요건 충족, 90일 기준을 교육용 가정으로 표시했습니다. 시스템은 장려금을 스스로 깎지 않고 회계·자금팀이 결정합니다. 공정위 2024년 가구 3사 사례는 일반 결론이 아니라 이 설계를 택한 근거로만 인용했습니다.
② 실제 지급 수취계좌와 은행 처리 결과: 모의 은행으로 대체했습니다. 실입금 계좌가 다르면 단정하지 않고 확인을 요청합니다.
③ 승인 당시 정정·소명 이력: 이 시스템이 이후 이력을 쌓고, 정정은 덮어쓰지 않습니다.
④ 마스터 정정 신고: 부서 주장으로 받습니다.

미수금 연령표의 연체일은 2026-06-30 기준 원본 값을 쓰고, 이후 상계·입금은 원본 행을 바꾸지 않고 조정 기록으로 쌓습니다. 식별정보 일치는 부정의 증거가 아니라 합산과 소명의 근거로만 씁니다. AI는 계산·판정을 하지 않고, 출력은 스키마와 원문 대조로 검증한 뒤 사람이 확인합니다.

(718자, 공백 포함)

## 문항 7(선택). AI·사람·도구의 역할 설계

판단의 근거가 되는 것은 결정적 코드가 맡고, 해석은 AI가, 결정은 사람이 맡도록 나눴습니다.

결정적 코드는 관련자 판정, 그룹 합산, 승인권자, 상계 제안액, 상태 전이를 담당합니다. 같은 입력이면 같은 결과가 나와야 감사와 소급 판단이 가능하기 때문입니다.

AI는 대리점의 자유 텍스트 회신을 구조화합니다. 요지, 사유, 언급한 증빙, 적힌 금액, 요청에 답하지 않은 것, 확인할 일입니다. 출력은 JSON 스키마와 허용 값으로 검증하고, 원문에 없는 금액이나 서류는 지우고 그 사실을 남깁니다. 무료 모델이 혼잡하면 다음 모델로, 실패하면 규칙 기반 해석으로 대체해 결정자가 늘 무언가를 보게 했습니다. 흐름은 AI를 기다리지 않습니다.

사람은 승인·반려·상계를 결정합니다. 결정 화면에는 AI가 찾은 미답변과 확인할 일이 체크리스트로 나옵니다. 결정자가 확인한 항목과 확인하지 않은 항목이 결정 사유와 감사 로그에 붙습니다. 그래서 AI 제안이 실제 판단에 어떻게 쓰였는지 사례별로 추적됩니다.

도구(지급 지시, 은행 전송, 미수금 조정, 통지)는 사람의 결정 뒤에 시스템이 실행합니다. 권한 없는 역할의 결정은 서버가 거부합니다.

이 구조는 개발 과정에도 적용했습니다. 원본 기준값을 테스트로 고정한 뒤 AI 코딩 도구로 구현했고, 매 단계 46개 통합 테스트로 검증했습니다.

(669자, 공백 포함)
