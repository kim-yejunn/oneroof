## 1. 문제와 전문성 확장 요약

| 항목 | 작성 내용 |
|---|---|
| 결과물 이름 | **OneRoof** — "이름은 달라도 한 지붕이면 한도도 하나" |
| 선택한 사용자·의사결정 | Corevia **영업지원팀**: 한 달 판매장려금을 접수해 대리점별 월 200만 원 이하를 전결 승인. **영업임원**: 한도를 넘는 건(관련자 합산 포함)을 승인·반려. **회계·자금팀**: 연체 미수금이 있는 대리점의 장려금을 상계할지, 전액 지급하고 따로 회수할지 결정. |
| 현재의 어려움 | ① **한도 쪼개기**: 원본 정책은 "대표자·주소·정산계좌 2개 이상 일치는 합산해 한도 적용"인데, 정산은 대리점 단위로 올라와 D-011·D-024·D-037 그룹(6월 합산 3,888,097원)이 1~5월 내내 영업지원팀 전결로 지급됐다. ② **자료 분산**: 대리점 마스터, 장려금 지급표, 실제 입금 계좌(회수 내역), 미수금 연령표가 따로 있다. ③ **부서 간 판단 충돌**: 영업은 지급을, 회계·자금은 연체 회수를 원하는데 지급 전에 마주칠 자리가 없다. ④ 정보가 정정되거나 반려되면 이미 지급된 건·대기 건을 어디까지 다시 볼지 정해져 있지 않다. |
| 기업 운영 안에서의 연결 | 앞: 영업(국내2팀) 실적 → 영업지원팀 정산 요청. 시스템: 관련자 판정 → 합산 한도 → 승인 라우팅 → 소명·계좌 확인 → 상계 결정 → 지급 지시 → 은행 회신 → 상태 갱신 → 감사 기록. 뒤: 회계·자금(미수금 잔액·지급 대사), 감사(이관 건). 확장 가능 연결: 출하 보류(신용 한도), 결산(미지급 장려금 충당). |
| 주업무의 시작과 종료 | **시작**: 영업지원팀이 "6월 정산 접수"(미지급 장려금 40건, 원본 지급표). **종료**: 각 장려금이 `지급 완료 / 상계 완료 / 반려 / 감사 중 보류` 중 하나가 되고, 지급 지시·미수금 잔액·감사 기록이 갱신된 상태. 그 상태가 다음 판단(다음 달 합산, 정정 시 소급 확인, 미수금 기준 상계)에 다시 쓰인다. |
| 본인의 관심·전문성 | 백엔드 개발자로서 이벤트 기반 업무 흐름과 데이터 정합성(트랜잭션 아웃박스, 중복 처리 방지, 감사 추적)을 내부통제 문제에 적용했다. "판정은 결정적 코드, AI는 해석 보조, 결정은 사람"이라는 원칙으로 권한 경계를 설계했다. |
| 필수 전문성 확장 | **연체 미수금 상계**(회계·자금 관점). 장려금 지급 직전 대리점의 90일 초과 연체 미수금(원본 연령표 `fin_ar_aging_cv.csv`)을 **조회**하고, 상계 제안액 = min(장려금, 연체 잔액)을 **계산**해, 회계·자금팀이 상계/전액 지급을 **판단**하면 지급 지시 금액·미수금 잔액·상계 통지 **상태를 변경**한다. 대리점이 이의를 제기하면 다시 판단한다. 위치: `payment/OverdueOffsetPolicy`, `payment/PaymentService`, `receivables/ReceivableAdjustments`, 화면 "채권·상계"·처리할 일(회계·자금팀). 증거: `OffsetFlowTests`, 감사 로그 `OFFSET_*`·`RECEIVABLE_*`. |
| 영향받는 다른 부서의 목표·제약 | **회계·자금팀**: 목표 = 연체 채권 회수, 제약 = 계약 근거 없는 장려금 삭감·미지급 금지(대리점법 취지, 참고 사례 2024-04 공정위 가구 3사). 상계는 같은 법인 사이 채권끼리만(민법 제492조 요건 — 계약 조항과 요건 충족은 **교육용 가정**). 주업무(장려금 지급)의 선택이 회계·자금의 회수 목표에 직접 영향을 준다. |
| 다른 부서 영향의 실제 반영 | 영업 승인을 받은 장려금이라도 90일 초과 연체 대리점이면 바로 은행으로 가지 않고 회계·자금팀 결정 대기로 바뀐다(대안 선택). 회계·자금팀 승인이 있어야 상계가 확정되고(승인), 지급 지시 금액이 줄고 미수금이 줄며 대리점에 상계 통지가 나간다(후속 처리). 대리점 이의 → 재검토 → 취소 시 미수금을 되살리고 전액 지급한다. 6월 실행: 상계 대상 21곳 중 D-034 는 입금(모의) 뒤 1,038,360원으로 재상신, D-012 는 이의 인정으로 상계 취소. |
| 확인할 개선 효과 | ① 관련자 합산 누락 0건: 6월 RPG-D-011 이 영업임원 결정으로 라우팅(전결 불가). 정정 후 1~3월·6월 전결분이 사후 확인으로 드러남. ② 확장 켬·끔 비교(화면 "채권·상계", 원본 기준 계산): 끔 = 장려금 37,159,812원 전액 현금, 켬 = 21곳 20,806,770원 상계·현금 16,353,042원(같은 금액 미수금 소멸). ③ 결정 기록 완결성: 모든 결정·회신·상태 변경이 감사 로그에 출처와 함께 남음. |

### 2-2. 핵심 관계와 연결 기준

- **관련자 판정**: 두 대리점의 대표자·주소·정산계좌 중 **2개 이상** 일치하면 연결, 연결을 **전이적으로** 묶어 그룹(원본 `data_dictionary.md` 정의). 계좌는 마스터 등록 값과 **실제 입금 계좌**를 함께 대조하고 근거마다 `마스터 등록 / 실제 입금 계좌`를 남긴다.
  원본 결과: 그룹 1개 D-011·D-024·D-037(대표자 동일, D-011·D-024 주소 일치, D-011·D-037 계좌 일치, D-024 는 실입금 계좌가 D-011 계좌). 근접 쌍(1개만 일치) D-034·D-041.
- **연결 키**: 장려금·미수금·입금은 `agency_id` 로, 결정·회신·지급은 사건 ID(`correlationId`)로 이어진다. 모든 원본 행은 `source_ref`(파일·줄 번호)를 가진다.
- **합산 기준**: 그룹 월 합산은 원본 상태가 `반려`인 건을 뺀다(지급되지 않았으므로). 원본 그룹 합산 01월 4,870,186 ~ 06월 3,888,097원, 개별 건 최대 1,867,253원(전부 단독 한도 안).

### 2-3. 상태·적용 시점·담당자·승인권한

- 기준일 2026-07-01(코드 `BusinessClock`). 식별정보는 적용일이 있어 "그 달 말 기준" 판정이 가능하다.
- 검토: `승인 대기 → 승인(지급 진행) → 지급 완료` / `소명 대기 → 재상신(2차) → 감사 이관` / `재분류로 대체`(정정으로 단위가 바뀜).
- 지급 지시: `상계 검토 → 상계 완료` 또는 `→ 지시 생성 → 은행 회신 대기 → 지급 완료/이체 실패`, `지급 보류`(계좌 미확인), `상계 이의`.
- 승인권한: 200만 원 이하 단독 = 영업지원팀, 초과·관련자 합산 초과 = 영업임원(원본 정책 그대로), 상계 = 회계·자금팀(추가 역할, 교육용 가정). 권한 없는 역할의 결정은 서버가 거부(403).

### 2-4. 판단 규칙과 제약

- 원본 제약은 가정으로 없애지 않는다: 한도 200만 원, 관련자 합산, 승인 권한.
- 관계 정황은 부정 확정이 아니다: 식별정보 일치는 합산과 **소명 요청**의 근거. 그룹 1차 반려 = 관계 소명 요청, 소명 회신 → 2차 상신, 2차 반려·무응답 → 감사 이관 + 장려금 `감사 중 보류`(삭감 아님).
- 시스템과 AI는 상신까지만, 승인·반려·상계 결정은 사람 역할이 누른다. AI는 계산·판정을 하지 않는다.

### 2-5. 업무모델이 조회·계산·판단·승인·후속 작업을 잇는 위치

정산 접수(`intake`) → 한도 단위별 검토 생성(`rebate`, 관련자 판정 `relatedparty`) → 승인(`approval`) → 지급 요청 → 상계 검토·계좌 확인(`payment`, 미수금 `receivables`) → 은행 전송·회신 → 지급 완료(`rebate`). 각 단계는 이벤트로 이어지고 이벤트는 같은 트랜잭션으로 저장(트랜잭션 아웃박스)된다.
**변경의 영향 확인**: 마스터 정정이 들어오면(`MasterChangeImpact`) 결정 전 검토 중 한도 단위가 바뀐 것은 대체·철회·재상신하고, 결정된 달은 다시 열지 않되 정정 값 때문에 임원 대상이 된 전결 월은 사후 확인을 만든다. 모의 입금이 들어오면 결정 전 상계 제안을 새 잔액으로 다시 상신하거나 연체 해소 시 철회한다.

### 2-6. 제공 BPMN 에서 바꾼 것

| 바꾼 점 | 이유 | 원본 제약·권한과의 관계 |
|---|---|---|
| "등록정보·한도 검토"를 수작업에서 **관련자 판정 엔진**으로 | 자료 분산이 합산 누락의 원인 | 판정 규칙·한도는 원본 정책 그대로 |

| 지급 전 **회계·자금 상계 결정** 단계 추가 | 회수 목표와 지급의 충돌을 지급 전에 다룸 | 추가 역할·상계 조항·90일 기준은 교육용 가정, 장려금을 스스로 깎지 않음 |

| **정보 정정 시 소급 재검토** | "정정 후 기존 승인·지급 예정 건을 어디까지 재검토할 것인가" | 지급은 되돌리지 않고 임원 사후 확인만 요청 |

- **상황·근거·대안 확인 뒤 생성·갱신되는 것과 다음 판단 반영**: 검토·승인 요청·지급 지시·미수금 조정·소명 요청·감사 이관이 생성·갱신된다. 미수금 조정은 다음 상계 판단의 잔액이 되고, 정정 이력은 이후 모든 월 판정에 쓰이며, 결정·회신 기록은 소급 확인과 감사 이관의 근거가 된다.
- **AI 역할**: 입력 = 요청 전문 + 대리점 회신 원문. 출력 = 요지·회신 구분·사유·언급한 증빙·적힌 금액·답하지 않은 것·확인할 일(JSON, 스키마·허용 값 검증, 원문에 없는 금액·증빙 제외). 사용 위치 = 소명·이의 결정 화면의 체크리스트. 사람은 확인한 항목을 체크하고 결정하며, 체크 결과가 결정 사유와 감사 로그에 `[회신 해석 #id 제안 k/n건 확인: …]` 로 남는다. 도구 실행(지급·상계·보류)은 사람 결정 뒤 구현이 한다. 모델: Gemini 무료 등급(혼잡 시 다음 모델 → 실패 시 규칙 기반, 기록에 표시).
- **예상 효과 산정**: 원본 6월 장려금·미수금으로 상계 켬·끔을 계산(`/api/offsets/comparison`). 비용·시간 제약: 모든 처리가 0.5코어·1GB 컨테이너에서 묶음 이벤트로 동작(아래 측정).
- **확인된 효과와 추정 구분**: 확인 = 관련자 합산 라우팅, 소급 발견 4건, 상계 21곳 20,806,770원(원본 기준 계산). 모의 = 은행·대리점 회신. 추정 없음. 조건 변경(정정·입금·이의) 시 판단과 후속 처리가 바뀌는 것을 위 사례와 테스트로 확인.
- **필수 확장 사용 지점**: 정상 사례의 일괄 승인 직후(상계 검토 18건), 변경 ②(입금 → 재계산), 정보 부족(이의 → 취소). 기록: 감사 로그 `OFFSET_PROPOSED`·`OFFSET_SETTLED`·`OFFSET_REVISED`·`OFFSET_CANCELLED`·`RECEIVABLE_OFFSET(_REVERSED)`.
- **다른 부서 영향 반영**: 회계·자금팀의 승인 없이는 상계가 확정되지 않고, 회계·자금 결정이 지급 지시 금액·미수금 잔액·대리점 통지를 바꾼다.

## 5. 실행·재현 방법

- **결과물 위치**: https://oneroof-17dq.axhub.app (로그인 없음). 소스는 이 저장소 `app/`.
- **도구·버전**: Java 21(빌드 도구는 JDK 17로 실행), Spring Boot 4.1, Spring Modulith 2.1, PostgreSQL 18, Node 20+·Vite·React 19, Docker. AI는 Gemini 무료 API(OpenAI 호환 주소), 키는 `app/.env`(형식 `app/.env.example`), 없으면 규칙 기반.
- **원본 데이터**: `app/src/main/resources/original/`(참가자 원본 4개 파일 복사본, 수정 없음). 앱이 빈 DB로 시작하면 웹 서버가 열리기 전에 자동 적재(`OriginalDataSeeder`), 체크섬 검증.
- **로컬 실행**: `app/README.md` "실행" 절(`docker build`, `docker run --env-file .env`). 테스트: `./gradlew test`(46개, Docker 필요, 모델 호출 없음).
- **대표 사례 입력과 순서**: 영업지원팀 → 처리할 일 "정산 접수" → "한도 이내 37건 일괄 승인" → 지급 "이체 완료 회신" / 영업임원 → RPG-D-011 반려 → 영업지원팀 → 변경·예외에서 소명 회신 입력 → 영업임원 → 재상신 건 체크 후 승인 / 회계·자금팀 → 채권·상계 비교 확인 → "상계 제안 일괄 결정" → 변경·예외에서 D-012 상계 이의 입력 → 회계·자금팀 재검토. 정정은 변경·예외 "시연 예시 채우기", 입금은 채권·상계 대리점 행 "입금".
- **모의 승인·회신 입력**: 은행 = 지급 화면 버튼, 대리점 = 변경·예외의 요청 카드(회신 문장 입력 + 회신 종류 버튼, "기한 경과" 버튼은 무응답).
- **결과 확인 위치**: 각 화면 상태 배지, 정산 현황, 감사 로그(검색), API(`/api/payments`, `/api/approvals/pending?role=…`, `/api/clarifications`, `/api/offsets/comparison`, `/api/audit`).
- **초기화와 제약**: 로컬은 `ONEROOF_DEMO_RESET_KEY` 를 두면 시연 도우미에서 초기화. **공개 서버는 초기화가 꺼져 있어 한 번 처리한 상태가 남는다.** 로그인 없는 시연 환경(역할 헤더로 역할 흉내, 권한은 서버가 검사) — 실제 운영 전환 조건은 `app/README.md` 접근 통제 절.
